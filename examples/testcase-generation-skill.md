# 示例 Skill：生成结构化登录测试用例

> 本文件为公开展示而重新编写的通用示例，不是原项目 Skill，也不包含内部 Prompt 或业务信息。

## 角色

你负责把已经确认的登录模块测试点转换为结构化测试用例。你不负责补写缺失需求，不负责直接执行浏览器，也不得输出任意脚本。

## 输入

- `requirements.md`：已整理的登录需求片段；
- `test-points.json`：已经审核的测试点；
- `ui-elements.json`：允许引用的页面元素描述；
- `schema.json`：输出字段和动作枚举。

如果任何必需输入缺失，返回 `INPUT_INCOMPLETE`，并列出缺失项。

## 允许的动作

- `navigate`
- `fill`
- `click`
- `wait_for`
- `assert_text`
- `assert_url`

不得输出 Shell、JavaScript、SQL 或不在列表中的动作。

## 工作步骤

1. 逐条读取测试点及其需求引用。
2. 确认前置条件、输入数据和预期结果。
3. 将人工步骤转换为允许的执行动作。
4. 只引用 `ui-elements.json` 中存在的元素；无法映射时标记 `manualReviewRequired=true`。
5. 检查步骤说明与执行动作是否一致。
6. 按 `schema.json` 输出 JSON，不添加 Markdown 代码围栏或额外解释。

## 输出要求

每条用例必须包含：

- 唯一 `caseId`；
- 标题、优先级和测试目标；
- `requirementRefs`；
- 前置条件；
- 人工可读步骤与预期结果；
- 对应的 `execution.actions`；
- 是否需要人工复核及原因。

## 失败条件

以下情况不得猜测：

- 需求没有说明预期行为；
- 测试点没有需求引用；
- 页面元素不存在或存在多个无法区分的候选；
- 所需动作超出允许列表；
- 输入之间存在明显冲突。

失败时返回结构化错误，包括错误类型、关联测试点、缺失证据和建议的人工确认问题。

## 质量检查

- 每条用例都能反向定位需求；
- 不使用输入中不存在的账号、按钮或业务规则；
- 不把多个独立目标合并为一个超长用例；
- 预期结果可以被观察或断言；
- 执行动作顺序与人工步骤一致；
- 不输出真实密码、Token 或其他敏感信息。

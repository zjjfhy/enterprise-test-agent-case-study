# 架构、职责边界与工程决策

## 1. 为什么不能“一次调用生成最终结果”

从需求材料直接生成最终测试报告，看起来链路最短，但会把多个不同性质的问题混在一次模型调用中：

- 输入是否解析完整；
- 图表与正文是否正确关联；
- 测试点是否覆盖主链路、边界和异常场景；
- 用例字段是否完整；
- 执行动作是否可以被浏览器执行；
- 执行失败来自用例、页面还是测试环境；
- 修复是否改变了原始需求语义。

如果没有阶段边界，失败时只能看到“结果不对”，无法判断应修改数据、Prompt、Skill、协议还是执行器。因此系统采用分阶段工作流，每一阶段产生可检查的中间产物，并为失败保留证据。

## 2. 分层架构

### 输入与理解层

负责解析文档、识别标题层级、正文、表格、流程图和 UI 截图，并保存来源位置。研究版本进一步利用版面与空间信息，减少图表和上下文错配。

### 生成与审查层

先生成测试点，再生成结构化测试用例。生成器负责产生候选结果，审查或裁决模块负责发现遗漏、重复、不一致和缺少证据的问题，并驱动增量补全。

### 协议与服务层

通过 JSON 协议连接模型输出与业务服务。Java 服务管理任务、状态、会话、日志和持久化；Python 服务承担文档处理和模型相关能力。协议版本独立于具体模型，避免模型更换直接影响执行器。

### 执行与反馈层

Playwright 将白名单动作转换为真实浏览器操作，记录步骤日志、当前 URL、DOM 摘要和截图。失败反馈必须包含可定位证据，不能只返回自然语言错误。

### 交付层

汇总用例、步骤、执行结果、错误信息和截图，生成适合人工审阅的多页 HTML 报告。报告既是交付产物，也是后续复盘和回归测试的数据来源。

## 3. Workflow、Skill、Tool 与服务的边界

| 概念 | 负责什么 | 不负责什么 |
|---|---|---|
| Workflow | 阶段顺序、状态流转、条件分支和终止条件 | 不直接提供权限安全 |
| Skill | 单阶段职责、上下文、工具使用方式和输出契约 | 不能保证模型一定遵守，也不是运行时隔离 |
| Tool | 提供受控、可审计的确定性能力 | 不自主决定长期目标 |
| 业务服务 | 权限、校验、事务、持久化、限流和审计 | 不应把所有业务判断交给模型 |
| Worker | 执行具体任务并上报状态 | 不等同于拥有独立目标的多 Agent |

该系统更准确的定义是“多阶段 Agent Workflow 加并行 Worker”，而不是把每一个节点都包装成独立 Agent。

## 4. 双路线设计

### 传统模型服务

适用于输入输出稳定、流程明确、成本和延迟需要预测的任务。优点是容易测试、监控和降级；不足是面对复杂文档或执行失败时适应能力有限。

### Agent 工作区

适用于需要读取文件、调用工具并根据反馈迭代的任务。优点是能够处理复杂上下文和多步问题；不足是耗时、Token 和输出稳定性更难控制。

### 统一边界

无论走哪条路线，最终都必须经过同一协议和服务端校验。Agent 超时、连续输出非法协议或达到预算上限时，系统可以回退到基础生成能力或进入人工处理。

## 5. 任务状态与并发

任务不只存在于单个进程的内存中，而是保存到持久化任务表。Worker 领取任务时使用带旧状态条件的原子更新：只有仍处于 `QUEUED` 的任务才能被更新为 `RUNNING`，并根据受影响行数判断是否领取成功。

为避免 Worker 异常退出后任务永久停留在运行状态，任务还需要：

- 领取者标识；
- 领取时间和租约；
- 进度心跳；
- 最大执行时间；
- 重试次数和最后错误；
- 可恢复的阶段输出。

单个服务实例内部使用有界线程池或信号量控制并发。浏览器实例消耗内存明显，不能仅根据 CPU 数量无限增加并发。

## 6. 定位器降级

执行器优先选择稳定、语义化并且对页面布局不敏感的定位方式：

```text
测试 ID
  -> role 与可访问名称
  -> label
  -> 稳定属性与文本
  -> CSS
  -> XPath
```

失败时返回当前 URL、目标描述、候选元素、DOM 摘要、页面截图和具体异常。绝对 XPath 虽然容易生成，但页面层级调整后容易失效，因此不作为首选。

## 7. 为什么最多修复三轮

三轮不是模型能力的理论上限，而是工程预算：

- 第一轮通常可以修复明显的定位器或等待问题；
- 后续轮次收益递减，并增加 Token、耗时和副作用；
- 连续相同错误更可能来自环境、需求或协议，而不是缺少一次模型调用；
- 必须为人工接管提供明确节点。

除轮次外，还应同时设置总时长、Token 和工具调用次数上限。检测到相同错误签名、无有效修改或测试环境不可用时，可以提前终止。

## 8. 为什么没有把MCP写成已落地事实

现有项目材料能够证明 Skill、工具调用、结构化协议和 Agent 工作流经验，但不能证明项目已使用 MCP。因此公开复盘不把内部接口包装成 MCP 实践。

如果后续需要将能力 MCP 化，候选工具可以包括文档解析、测试点查询、用例校验、浏览器执行状态查询和报告获取。但即使使用 MCP，权限、参数校验、任务幂等、超时和审计仍需由服务端实现，不能依赖协议本身解决。

## 9. 设计原则总结

1. 不把输出格式正确等同于语义正确。
2. 不把执行通过等同于业务正确。
3. 不把 Skill 当作安全边界。
4. 不把节点数量包装成多 Agent。
5. 不让模型直接拥有无限重试和任意执行权限。
6. 所有关键阶段都应有可复现的输入、版本和证据。

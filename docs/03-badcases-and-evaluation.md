# Badcase、指标口径与回归评测

## 1. 为什么必须保留 Badcase

Agent 系统的主要风险不是完全不能运行，而是大部分时间看起来正常、少数场景产生难以复现的错误。如果没有输入、模型版本、Skill 版本、工具日志和执行证据，团队只能反复调整 Prompt，却无法确认问题是否真正得到解决。

因此，Badcase 不只是错误样例，而是包含完整上下文的回归资产。

## 2. Badcase A：格式正确，语义不可执行

### 现象

模型输出通过 JSON Schema 校验，但 `click` 动作的目标只是自然语言描述，页面中不存在稳定匹配元素。

### 根因

格式校验只能判断字段与类型，不能验证目标元素是否存在，也不能判断描述是否唯一。

### 改进

- 执行前进行 DOM 探测；
- 优先生成语义化定位信息；
- 将候选元素与置信度返回执行器；
- 候选不唯一时停止猜测；
- 记录原始描述与最终定位器之间的映射。

### 回归点

- 页面存在唯一稳定元素时应正常执行；
- 同名按钮出现多个时应要求补充上下文；
- 不存在目标元素时应返回可解释失败，不能构造虚假定位器。

## 3. Badcase B：页面调整导致定位器失效

### 现象

原有绝对 XPath 在页面布局调整后失效，相关用例集中报元素未找到。

### 根因

定位策略依赖 DOM 层级，而不是元素语义。

### 改进

- 优先测试 ID、role、可访问名称和 label；
- 统一定位器降级顺序；
- 失败时采集候选元素和页面截图；
- 区分“目标不存在”和“定位器不稳定”。

### 回归点

- 仅改变外层布局时，核心用例仍应通过；
- 文案轻微变化时，不应依赖模糊文本误点其他元素；
- 出现多个候选元素时，不应默认点击第一个。

## 4. Badcase C：修复循环没有新增信息

### 现象

模型连续多轮生成不同文本，但底层定位器和错误类型没有实质变化。

### 根因

系统只记录自然语言错误，没有比较错误签名、动作差异和修复收益。

### 改进

- 为错误生成稳定签名；
- 比较修复前后的动作和定位器；
- 连续同类错误提前终止；
- 同时设置轮次、时长和 Token 上限；
- 将完整修复历史交给人工，而不是覆盖旧版本。

### 回归点

- 有有效修改时允许继续；
- 无有效修改时应在上限前停止；
- 环境错误不能被分类为用例可修复错误。

## 5. 指标体系

### 输入层

- 解析成功率；
- 标题层级保留率；
- 图表与关联文本匹配质量；
- 来源定位完整率。

### 生成层

- JSON 协议合法率；
- 需求逻辑覆盖率；
- 重复用例比例；
- 幻觉或无来源实体比例；
- 人工可用率。

### 执行层

- 可执行用例比例；
- 首轮执行通过率；
- 修复后通过率；
- 平均修复轮数；
- 按错误类型统计的失败率。

### 系统层

- 端到端耗时；
- 单阶段 P50/P95 时延；
- Token 与模型调用成本；
- 超时、降级和人工接管比例；
- Worker 异常恢复情况。

## 6. 口径说明

### 一次生成可用率

表示生成结果经过项目约定的人工检查后，可以进入后续审阅或执行流程的比例。它不等于协议合法率，也不等于自动执行通过率。

### 需求逻辑覆盖率

将生成结果与人工基准中定义的需求逻辑进行匹配，衡量需求场景是否被覆盖。具体匹配与判定方法应以研究实验定义为准。

### 执行通过率

衡量用例在指定测试环境和版本中能否完成自动执行。它会受到测试数据、页面状态、环境稳定性和定位器质量影响，不能单独代表业务正确性。

## 7. 回归集结构

建议每条回归样例保留：

```text
case_id
input_version
requirement_reference
expected_test_points
expected_constraints
allowed_actions
model_version
skill_version
tool_version
actual_output
execution_result
error_category
review_result
```

回归集需要覆盖：

- 正常主链路；
- 空值、边界值和异常输入；
- 权限和状态变化；
- 图文关联；
- 页面轻微改版；
- 环境不可用；
- 模型输出格式错误；
- 连续修复无收益。

## 8. 发布前比较

每次更新模型、Prompt、Skill 或协议，应至少比较：

- 总体质量是否提升；
- 是否只改善某一类样例；
- 是否引入新的失败类型；
- 时延和成本是否可接受；
- 降级和人工接管是否仍然有效。

不能只展示成功案例。稳定的 Agent 交付需要同时报告效果、成本、失败率与适用边界。

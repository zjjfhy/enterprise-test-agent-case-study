# Skill 设计方法与检查清单

## 1. Skill 的定位

Skill 用来约束某一类任务的行为方式：告诉 Agent 当前阶段要解决什么问题、可以读取哪些输入、可以调用哪些工具、必须输出什么结构，以及在什么情况下停止或报告失败。

Skill 不是一段越长越好的 Prompt，也不是权限、安全或运行时隔离机制。模型输出即使符合 Skill，也必须经过服务端校验。

## 2. 一个完整 Skill 的组成

### 身份与目标

用一句话定义职责，避免同时承担分析、生成、执行和修复等多个目标。

### 输入

明确输入文件、结构和可信程度。例如需求片段、测试点、DOM 摘要分别属于不同类型的上下文，不能默认它们都正确。

### 输出契约

说明输出字段、类型、枚举、必填项和版本。可以用 JSON Schema 做格式校验，但还要增加业务校验。

### 工具与权限

列出允许使用的工具以及每个工具的参数边界。未列出的工具默认不可用；高风险动作需要额外确认。

### 工作步骤

给出推荐步骤，但避免写成无法适应异常输入的死流程。每一步都应对应可检查的中间结果。

### 失败条件

明确何时不得继续猜测，例如输入缺失、需求证据不足、实体无法对应、工具连续失败或达到预算上限。

### 示例与反例

正确示例帮助模型理解目标，反例帮助模型识别常见错误。示例必须覆盖边界，而不只是最理想路径。

## 3. 输入分析 Skill

重点不是立即生成用例，而是回答：

- 输入文件是否齐全；
- 哪些内容可解析、哪些内容需要人工确认；
- 标题、正文、图表和 UI 截图之间如何关联；
- 是否存在无法定位来源的关键信息；
- 后续阶段应该使用哪些结构化产物。

输入分析阶段发现材料缺失时，应输出缺失清单，而不是补写不存在的需求。

## 4. 测试点生成 Skill

每个测试点至少包含：

- 测试目标；
- 对应需求证据；
- 正向或异常类型；
- 前置条件；
- 关键变量和边界；
- 尚未确认的问题。

生成完成后应检查主链路、边界条件、异常分支、权限、状态变化和数据一致性，避免只生成“输入正确值并提交”一类正向场景。

## 5. 可执行用例生成 Skill

该阶段要把面向人的步骤转换为机器可执行动作，但不能让模型输出任意脚本。推荐使用有限动作集合，并通过字段引用保持阅读步骤和执行步骤一致。

如果某一步无法可靠自动化，应该标记为人工步骤或不可执行原因，而不是编造选择器和接口。

## 6. 自动执行 Skill

执行阶段应遵循：

- 每一步执行前验证参数；
- 每一步执行后保存结果；
- 失败时保存页面、日志和候选元素；
- 不因为个别失败删除原始用例；
- 不在环境异常时持续要求模型修改用例；
- 达到预算或轮次上限后进入人工处理。

## 7. Skill 评审清单

- [ ] 是否只有一个清晰职责？
- [ ] 是否说明输入来源和可信边界？
- [ ] 是否有版本化输出契约？
- [ ] 是否限制了工具和高风险动作？
- [ ] 是否定义了失败与终止条件？
- [ ] 是否区分格式错误和语义错误？
- [ ] 是否包含正确示例、边界示例和反例？
- [ ] 是否要求保留来源与证据？
- [ ] 是否设置时间、Token 和工具调用预算？
- [ ] 是否可以被固定回归集重复验证？

## 8. Skill 版本管理

每次执行至少记录：

- Skill 名称和版本；
- 模型与参数；
- 输入数据版本；
- 工具版本；
- 输出与错误类型；
- 时延和 Token；
- 是否触发重试或降级。

修改 Skill 后应在固定回归集上比较质量、时延和成本，而不是只凭几个成功样例判断效果。
